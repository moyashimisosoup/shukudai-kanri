# 期間・目標日の呼び名を設定可能にする設計メモ

## 目的と前提

現在の画面は、日付範囲を「夏休み」、終了日時を「おわり」と呼ぶことを前提にしている。本メモでは、同じ進捗管理を冬休み、学期末、発表会、入試などにも使えるようにする案を整理する。

例として、次のような表示を可能にしたい。

- 子ども向け：`にゅうしとうじつまで あと 20日`
- 大人向け：`入試当日まで あと20日`
- 進捗比較：`受験勉強の経過 65%`

ここではコード変更は行わない。行番号は調査時点のものであり、実装時には併記した文字列や関数名でも確認すること。

### 変えるもの・変えなくてよいもののまとめ

利用者が変えられるべきなのは、子ども画面、保護者画面、共有用テキストに繰り返し現れ、家庭ごとの用途を説明する次の値である。

- 期間の呼び名（例：`夏休み`、`受験勉強`）
- 期間のかな表記（例：`なつやすみ`、`じゅけんべんきょう`）
- 目標日の呼び名（例：`夏休み終了`、`入試当日`）
- 目標日のかな表記（例：`なつやすみ おわり`、`にゅうしとうじつ`）
- 必要なら、期間名に連動する自動タイトル

一方、次は利用者設定にしなくてよい。

- 旧タイトルを見分けるための過去の文字列
- ソースコードやCSSのコメント
- 辞書の読み込みが「おわりました」という別用途の文言
- ミニコンテンツの文章。残すか汎用文へ一度だけ直す
- JS起動前のHTMLフォールバックやホーム画面名。固定の汎用名へ一度だけ直す

## 設定データ案

### 最小案

既存の `startAt`、`endAt` はそのまま使い、同じ `config` に次の4項目を加える。

```js
periodLabel: '夏休み',
periodLabelKana: 'なつやすみ',
deadlineLabel: '夏休み終了',
deadlineLabelKana: 'なつやすみ おわり'
```

`deadlineLabel` は単なる「終了」の言い換えではなく、`まで あと20日` の直前にそのまま置ける名詞句とする。これにより次の設定ができる。

```js
periodLabel: '受験勉強',
periodLabelKana: 'じゅけんべんきょう',
deadlineLabel: '入試当日',
deadlineLabelKana: 'にゅうしとうじつ'
```

主な組み立ては次のようになる。

| 場所 | 組み立て例 |
|---|---|
| 子どものカウントダウン | `deadlineLabelKana + 'まで'` |
| 子どものペース行 | `periodLabelKana` |
| 保護者の残り時間 | `deadlineLabel + 'まで'` または `deadlineLabel + 'まであと'` |
| 保護者の経過率 | `periodLabel + 'の経過'` |
| テキスト要約 | `deadlineLabel + 'まで あと…'`、`periodLabel + 'の経過…'` |

終了後の文章は助詞との相性が難しい。`入試当日は終了しました` は意味が変わるため、固定の文型で無理に共用しない方がよい。

- 案A：`deadlineLabel + 'を すぎました'`（`入試当日をすぎました` は自然だが、`夏休み終了をすぎました` はやや硬い）
- 案B：`periodLabel + 'は おわりました'`（期間には自然だが、期間名を `入試` とした場合は不自然）
- 案C：終了後メッセージも別入力にする（自然さは最大だが設定項目が増える）
- 案D：用途プリセットごとに終了後文型を持ち、自由入力時だけ汎用の `目標日時を過ぎました` を使う（実用上は安定するが実装とテストが増える）

最小実装なら案Dの簡略形、すなわち自由入力では固定の汎用文を使うのが安全である。

### タイトルとの関係

現在、タイトルは設定で変更できる一方、名前が入ると既定値が `〈名前〉の夏休みの宿題` になる。期間名だけを変えてタイトルが夏休みのままでは、一般化が不完全に見える。ただし、既存のカスタムタイトルを自動で書き換えてはいけない。

選択肢は次のとおり。

- 案A：タイトルは独立したままにする。期間名を変えても自動変更しない。
  - 長所：既存動作への影響が最小で、誤判定による上書きがない。
  - 短所：利用者がタイトルも手で直す必要があり、`夏休み` が残りやすい。
- 案B：現在のタイトルが既知の自動生成形である場合だけ、`〈名前〉の〈期間名〉の宿題` へ更新する。
  - 長所：多くの既存利用者には自然で、カスタムタイトルをおおむね保護できる。
  - 短所：偶然同じ文字列を手入力した人を見分けられない。また `受験勉強の宿題` など、用途によって語尾が不自然になりうる。
- 案C：`titleMode: 'auto' | 'custom'` と、必要ならタイトルひな形を追加する。
  - 長所：一度移行した後は自動・手動を明確に区別できる。
  - 短所：移行時の初回だけは推測が必要で、設定UIと同期項目が増える。ひな形の自由入力まで許すと入力検証も必要になる。

将来も名前や期間との自動連動を続けるなら案Cが堅い。初回移行では現在の `isGeneratedTitle()` が認識するものだけを `auto`、それ以外を `custom` と推定する。これは現行も同じ文字列を自動生成扱いしているため、既存利用者に新しい種類の上書き事故を増やしにくい。

ただし、自動タイトルの文型を固定するか、プリセットごとに持つかは別の判断として残す。

## かな表記を用意する方法

自由入力された漢字から、正しいかなを常に機械生成することはできない。人名、学校名、固有名詞、`本番` のような複数の読みを持つ語があるためである。

### 案1：漢字欄とかな欄を対で入力する

`期間の呼び名` と `こども画面でのよみ`、`目標日の呼び名` と `こども画面でのよみ` をそれぞれ入力してもらう。

- 長所：オフラインで確実に動き、固有名詞や家庭独自の呼び方にも対応できる。
- 短所：入力欄が4つになり、保護者の負担が大きい。かな欄にも漢字を入れられるため、検証や説明が要る。
- 補足：かな欄は空を許し、空なら漢字欄をそのまま表示するフォールバックにすると保存不能にはならない。ただし子どもが読める保証はなくなる。

### 案2：プリセットを選び、自由入力のときだけ対で入力する

例として `夏休み`、`冬休み`、`春休み`、`学期末まで`、`入試まで`、`自由入力` を用意し、プリセットには漢字・かな・終了後文型を組で持たせる。

- 長所：一般的な用途は選ぶだけで済み、かなの入力ミスも減る。終了後の文章も自然にしやすい。
- 短所：プリセットの選定・保守が必要で、選択肢が多いと逆に探しにくい。自由入力の問題自体は残る。
- 補足：最小限のプリセットと「自由入力」に絞るなら、案1の負担を実用的に減らせる。

### 案3：既存の漢字読み替え機能を使って候補を作り、利用者が確認する

アプリ内の辞書・読める漢字の仕組みでかな候補を出し、保存前に保護者が直す。

- 長所：既存資産を再利用でき、かな欄を一から入力する量を減らせる。
- 短所：任意の固有名詞を読める保証がない。辞書未読み込み、辞書外語、複数読みの選択があり、無確認の自動確定には向かない。短い設定のために辞書読み込みを待たせる可能性もある。
- 補足：自動変換ではなく、案1の入力補助としてのみ使うのが安全である。

### 案4：外部の読み変換サービスを使う

- 長所：辞書の語彙をアプリ本体に持たず、幅広い候補を出せる可能性がある。
- 短所：通信不能時に使えず、入力語を外部へ送るプライバシー説明、利用料、サービス停止、誤読への対処が必要になる。このアプリの端末内保存を重視する性格とも合いにくい。

### 案5：子ども画面にも漢字欄をそのまま出す

- 長所：追加設定が2項目で済み、実装が最小になる。
- 短所：読める漢字の設定がある現在の設計と矛盾し、低学年の子どもが読めない可能性が高い。「子ども向けかな表記」を維持する要件を満たさない。

現実的な中心案は案2と案1の組み合わせである。案3は任意の入力補助として追加できるが、正解を保証するものとしては扱わない。

## 基本設定に出すか、詳細設定に隠すか

### 案A：4項目すべてを基本設定に出す

- 長所：開始日・終了日と意味が一続きで、用途変更時に見落としにくい。
- 短所：現在3項目しかない基本設定が長くなり、夏休み用途の家庭にも不要な判断を求める。

### 案B：期間名と目標日名を基本設定、かな表記を詳細設定にする

- 長所：用途を決める主要2項目は見つけやすく、通常の画面は比較的短い。かなはプリセットから初期入力できる。
- 短所：自由入力でかな候補が作れない場合、詳細設定を開く必要に気づかない恐れがある。漢字とかながずれたまま保存されうる。
- 必要な対策：漢字欄を変更してかなが未確認なら、基本設定内に `こども画面のよみを確認` という状態表示・導線を出す。

### 案C：「表示のことば」という折りたたみを基本設定内に置く

- 長所：日付との関係を保ちつつ、普段は画面を短くできる。詳細設定という別ページを探させない。
- 短所：折りたたみは存在に気づかれにくく、ブラウザ標準の `details` を使う場合は開閉状態の扱いも決める必要がある。

### 案D：用途プリセットだけ基本設定、自由入力の詳細を選択時に展開する

- 長所：通常利用は最短で、自由入力を選んだ人だけ4項目を見る。漢字とかなの対応も崩れにくい。
- 短所：プリセットの設計が前提となり、「以前入力した自由設定に戻す」など状態管理が増える。

推奨寄りなのは案D、プリセットを設けないなら案Bである。ただし、かな未確認を黙って詳細設定へ隠さないことが条件になる。

## 既存設定を壊さない移行

### 原則

- 既存の `title`、`childName`、`startAt`、`endAt`、課題、進捗には触れない。
- 新項目がない設定は、現在と同じ表示になる既定値を読み取り時に補う。
- 読み取りだけを理由に起動直後の `saveCfg()` や同期送信をしない。現在の同期は設定全体の後勝ちであり、初回スナップショット前の自動保存が他端末の設定を初期値へ戻す危険が、既存コメントにも明記されている。
- カスタムタイトルを自動生成タイトルへ戻さない。

### 推奨する既定値

新項目がない既存設定には、メモリ上で次を補う。

```js
periodLabel: '夏休み'
periodLabelKana: 'なつやすみ'
deadlineLabel: '夏休み終了'
deadlineLabelKana: 'なつやすみ おわり'
```

これなら、移行直後の見た目と要約文をほぼ現在どおり維持できる。利用者が次に明示的な設定変更を保存した時点で、ほかの設定と一緒に新項目も保存・同期される。

### スキーマ番号を上げる場合の注意

現在の読み込みは `schema === SCHEMA`、または明示された一世代前の移行だけを受け入れ、それ以外は初期設定を作る。したがって、単純に6から7へ上げた新設定を旧版へ同期すると、旧版が未知のスキーマとして設定を初期化する危険がある。

選択肢は次のとおり。

- 案A：今回はスキーマを上げず、追加フィールドを `normalizeConfig()` で補う。
  - 長所：加算的な変更に合い、旧版も未知フィールドを通常は保持できる。
  - 短所：フィールド追加済みかをスキーマ番号だけでは判別できない。
- 案B：スキーマを上げる前に、旧版側へ「将来スキーマでも既知フィールドを保持して読む」互換リーダーを先行配布し、普及後に7を送る。
  - 長所：明示的な移行履歴を持てる。
  - 短所：二段階配布が必要で、全端末の更新を保証しにくい。

この変更はフィールド追加だけなので案Aが安全寄りである。もし `titleMode` など不可逆な意味変更まで含めるなら、混在バージョン試験をしたうえで案Bも検討する。

### タイトル移行の手順案

1. 既存タイトルが現在の `isGeneratedTitle()` に一致するか判定する。
2. 一致しないタイトルは必ずカスタムとして、その文字列をそのまま保つ。
3. 一致するタイトルも、初回読み込みだけでは書き換えない。
4. 利用者が期間名を変更した時点で、自動タイトルも変更するかをUI方針に従って決める。
5. `titleMode` を導入する場合は、その明示的な保存以後、文字列比較ではなくモードを正とする。

### 同期・入出力で確認すること

- 設定トレース対象 `TRACE_CONFIG_FIELDS` に新項目を追加するか。値そのものを残す場合の個人情報・長さも確認する。
- 共有中の新旧端末で、旧端末が保存しても未知フィールドが落ちないか。
- 設定のエクスポート／インポートが `config` の未知フィールドを保持するか。
- 空文字、極端に長い文字列、HTMLに見える入力を正規化・エスケープできるか。
- タイトルと同様に最大長を決めるか。画面幅を考えると、表示名は長文ではなく短い名詞句に制限する方がよい。

## 作業の分け方と大きさ

依存関係を考えると、次の順が安全である。

1. **表示文型と設定仕様を確定する（大）**
   - 期間名・目標日名の責務、終了後文、タイトル連動、空欄時の挙動を決める。
   - 日本語の自然さと後方互換の両方に影響するため、コード量以上に判断が大きい。
2. **設定の正規化と移行を実装する（大）**
   - 既定値、長さ制限、`titleMode` の有無、同期混在時の扱いを実装する。
   - 既存データを壊す可能性が最も高い部分で、回帰試験を先に用意したい。
3. **表示文言を一つの組み立て層へ集約する（中〜大）**
   - 子ども画面、保護者画面、要約の各所が別々に文字列を組み立てないよう、表示用関数へ寄せる。
   - 13か所を直接置換するだけだと助詞・終了後文が再び分岐するため、ここが実装の中心になる。
4. **設定UIとかな入力を実装する（中。プリセットや辞書補助を入れるなら大）**
   - 基本／詳細の配置、未確認表示、入力検証を追加する。
   - 4欄の自由入力だけなら中、プリセット・候補生成・状態保持まで行うと大きい。
5. **固定文言・コメント・初期HTMLを汎用化する（小）**
   - `data.js`、`style.css`、`index.html` と実装コメントを整理する。
   - `index.html` の文書タイトルと `h1` は同時に変更する。
6. **試験を追加する（大）**
   - 夏休み既定値、入試例、空欄、終了前後、カスタムタイトル保持、新旧同期、要約出力を確認する。
   - とくに「既存設定を開いただけで保存・同期されない」「旧版保存で新項目が消えない」を重点にする。

大きいのは、(1) 文型の決定、(2) 同期を含む移行、(6) 回帰試験である。文字列の置換そのものは小さいが、タイトル自動生成と新旧端末の設定全体同期があるため、移行を独立した作業として扱う必要がある。

## 実装前に残る判断事項

- 期間名を変えたとき、既定タイトルも自動変更するか。変更するなら `titleMode` を持つか。
- 終了後表示を、期間名から作るか、目標日名から作るか、汎用固定文にするか。
- プリセットを設けるか。設ける場合、最初に何種類まで含めるか。
- かな欄を必須にするか、空なら漢字表記へフォールバックするか。
- かな候補生成を初回から入れるか、まず対入力だけで出すか。
- 基本設定に4項目を出すか、主要2項目＋かな確認導線にするか。
- 製品名・ホーム画面名も今回汎用化するか。それとも家庭ごとの画面文言だけを対象にするか。
- スキーマ番号を維持するか、互換リーダーの先行配布を含む二段階移行にするか。

最小で安全な第一段階は、「4項目を追加し、既定値は現在と同じ、タイトルは既存文字列を保持、かなは対入力、終了後は汎用固定文、スキーマ番号は維持」である。プリセット、かな候補、自動タイトルは、その上に別段階で足せる。
