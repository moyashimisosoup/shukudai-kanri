# 3か月無操作データ削除 — 実装前仕様

Status: 提案（未実装）  
対象: 共有を設定した世帯の Firestore データ  
基準日: 2026-08-11

## 1. 結論

最後の「意味のある操作」から **90日** が過ぎた共有世帯を、サーバー側の定期処理で削除する。
削除時は先に `household_tombstones/<houseId>` を作り、同じトランザクションで
`households/<houseId>` を削除する。墓標は原則として期限を設けず残す。

Firestore の TTL だけで `households` を削除する方式は採らない。TTL 削除は非同期で、複数文書を
トランザクションとして削除できないため、削除と墓標作成の間に古いオフライン端末が文書を作り直す
余地が残る。主方式は Cloud Functions for Firebase の scheduled function とし、TTL は将来、墓標や
監査ログなど「単独で消してよい文書」の後始末にだけ使う。

ここでいう削除対象は運用者が管理する **Firestore 上の共有データ** である。端末の
`localStorage`、Firestore のブラウザ内キャッシュ、利用者自身が書き出した JSON バックアップまで
遠隔で完全消去することはできない。この範囲は利用者向け説明に明記する。

## 2. 現行構成と制約

現行は次の構成である。

- `households/<SHA-256(共有コード)>` の1文書に、暗号化済み `config` と `state`、平文の
  `configAt`、`stateAt`、`devices` を保存する。
- 鍵は共有コードから端末内で導出し、Firebase へ送らない。サーバーは内容を復号できない。
- `assets/app.js` は `localStorage` を先に読み、`assets/sync.js` があとから Firestore と合流する。
- Firestore の永続キャッシュにより、オフライン中の書き込みは端末内に滞留し、再接続後に送られる。
- 現行ルールは `households` のクライアント削除を禁止し、許可フィールドも
  `config`、`state`、`configAt`、`stateAt`、`devices` に限定している。
- 記録・本・進捗の訂正を同期するために暗号化された `state` 内に置く既存の削除印と、本仕様の
  **世帯文書そのものの墓標**は目的が異なる。混用しない。

静的クライアントだけでは、90日間一度も開かれていない端末や文書に処理を実行できない。
したがって、期限どおりの削除には Firebase 側で動く処理が必須である。

## 3. 「操作」と数えるもの

### 3.1 数える操作

共有世帯の誰かが次の操作を完了し、共有データへの変更が受理された時点を
`lastActivityAt` とする。世帯単位なので、親・子・複数端末のどれか1台の操作で90日の起算点が更新される。

- 宿題の進捗を追加、訂正、削除する
- 通常記録、本の記録、毎日の記録を追加、編集、削除する
- 宿題項目、夏休み期間、表示設定など `config` を変更する
- 子どもへのメッセージを変更する
- 共有端末を追加または外すなど、共有関係を意図的に変更する
- 警告画面の「このまま使う」を押す（閲覧中心の家庭にも明示的な延長手段を用意する）

実装時は「画面イベントが起きたこと」ではなく、変更が保存キューに入り、サーバーが受理したことを
基準にする。オフライン中の操作日は参考として端末内に持てるが、削除期限を延長する公式時刻は
再接続後に得たサーバー時刻とする。

### 3.2 数えない操作

- ページを開いただけ、タブを切り替えただけ、進捗を見ただけ
- snapshot の受信、起動時の自動接続、再描画
- 端末情報・アプリ版の自動登録、オンライン状態の確認
- 同じ内容の自動再送、マージ後の機械的な書き戻し
- バックアップ JSON の書き出しだけ（共有データを使い続ける意思は「このまま使う」で確認する）
- 失敗してサーバーに到達していない操作

単なる起動を数えないのは、ホーム画面や保護者画面を開きっぱなしにしただけで保存期限が無期限に
延びるのを防ぐためである。

## 4. 期限、予告、猶予

- 期限: `lastActivityAt + 90日`
- 予告開始: 残り30日（無操作60日）
- 強い予告: 残り7日（無操作83日）
- 最終表示: 残り24時間未満
- 削除実行: 期限経過後、1日1回の scheduled function が対象を処理する

アプリを開いた時だけ警告を表示できる。メールアドレスや Push 通知基盤を持たない現行構成では、
90日間まったく開かれなかった家庭へ事前連絡することはできない。この制約は説明文にも含める。

表示案:

- 残り30日: `共有データは、あと30日操作がないと削除されます`
- 残り7日: `共有データの削除まで あと7日です`
- 延長操作: `このまま使う`（押した時点から90日に戻す）
- 削除後: `この共有データは、長期間使われなかったため削除されました`

「3か月」は月の日数でぶれさせず、内部判定では 90 × 24時間を使う。表示は日単位に丸め、利用者の
ローカルタイムゾーンで示す。削除処理と判定は UTC の Firestore Timestamp で行う。

## 5. 保存するメタデータ

`households/<houseId>` に、内容とは別の平文メタデータを追加する。

```text
lastActivityAt   Firestore Timestamp  最後の意味のある操作のサーバー時刻
expiresAt        Firestore Timestamp  lastActivityAt + 90日（表示・検索用）
retentionVersion number               適用した保持方針の版
retentionEligibleAt Firestore Timestamp 段階導入時の最短削除可能日
```

`lastActivityAt` と `expiresAt` は宿題内容を含まないが、利用時期というメタデータではある。
E2E 暗号化の対象外であり、Firebase プロジェクト管理者には見えることを明記する。

クライアントの時計で期限を決めない。新しいクライアントは「操作があった」という合図を送り、
Cloud Function またはルールで検証した `serverTimestamp` を基準に更新する。既存クライアントとの
移行期間は、Firestore の document-written trigger が `config` または `state` の暗号文変更を検出し、
サーバー時刻を設定する方式を併用する。`devices` だけの自動更新は活動に数えない。

`firestore.rules` の `onlyKnownFields()` は上記フィールドを許可するよう更新が必要である。ただし、
クライアントが任意の未来時刻を書けない条件も同時に追加する。サーバー専用フィールドにする場合は、
クライアントの更新で既存値を変えていないことを `diff().affectedKeys()` で検証する。

## 6. 墓標とデータ復活防止

新しいコレクションを追加する。

```text
household_tombstones/<houseId>
  deletedAt       Firestore Timestamp
  reason          "inactive-v1"
  lastActivityAt  Firestore Timestamp
  policyVersion   number
```

墓標に名前、宿題、共有コード平文、暗号文は保存しない。ID は現在と同じ共有コードの SHA-256 であり、
`list` は常に禁止する。クライアントは自分が知る ID に対する `get` だけを許可し、create/update/delete は
サーバーだけに許可する。

`households/<houseId>` の create/update は、ルールで対応する墓標が存在しない場合だけ許可する。
Firestore Security Rules は `exists()` で別文書の存在を確認できる。ルール評価の従属読み取りには
課金が生じうるため、書き込み回数を基に費用を確認する。

削除ジョブはトランザクション内で次を行う。

1. household を読み直す。
2. `lastActivityAt`、`retentionEligibleAt`、現在時刻を再確認する。
3. まだ期限切れなら墓標を作る。
4. 同じトランザクションで household を削除する。

これにより、直前の活動更新とはトランザクション競合として再試行される。削除後は、新旧どちらの
クライアントが `setDoc(..., {merge:true})` を再送してもルールで拒否される。

新しいクライアントは接続前に墓標を確認し、見つかった場合は次を行う。

- 自動再接続と自動再送を止める
- その共有コードを端末から外し、同じコードでの新規作成を禁止する
- Firestore の保留書き込みが拒否されたことをエラーとして延々再試行しない
- アプリ管理下の `localStorage` と Firestore 永続キャッシュを安全に破棄する導線を実行する
- 新しく始める場合は、新しい共有コードを作るよう案内する

古い端末は墓標を理解できなくても、サーバールールが最終防壁になる。墓標を期限付きで消すと、さらに
古いオフライン端末がその後に復活させられるため、原則は無期限保持とする。墓標の総数・費用が問題に
なった時だけ、別の世代ID方式を設計して見直す。

既存の `metrics_households/<hash>` は登録数の重複防止用であり、墓標には使わない。権限と意味が違う。

## 7. TTL と Cloud Functions の選択

### 推奨: scheduled Cloud Function

- 1日1回、`expiresAt <= now` かつ `retentionEligibleAt <= now` をページ分割して取得する。
- 各文書を上記トランザクションで墓標化・削除する。
- 再実行しても同じ結果になる冪等処理にする。scheduled function は重複・並行実行があり得る前提で作る。
- 成功、競合で保留、失敗の件数だけを構造化ログへ出し、内容や共有IDは原則ログへ出さない。
- Functions のサービスアカウントは必要最小限の IAM 権限にする。

Cloud Functions の scheduled function は Cloud Scheduler を利用し、課金設定とデプロイが必要になる。
運用開始前に Blaze プラン、予算アラート、リージョン、日次ジョブの監視担当を決める。

### 非推奨: households への TTL 単独適用

Firestore TTL は期限切れ文書を自動削除できるが、削除は即時ではなく、通常は期限後24時間以内である。
また複数文書の削除をトランザクションにはできない。TTL 削除後の Function trigger で墓標を作る方式も、
削除から trigger 完了までの競合窓が残るため主方式にしない。

TTL を併用するなら、復活防止に影響しない運用ログや、将来「十分長く保持した後に消してよい」と決めた
墓標の後処理に限定する。

## 8. localStorage、キャッシュ、バックアップ

### localStorage と Firestore キャッシュ

サーバーは未起動端末の保存領域を消せない。新しい版を起動しオンラインになった端末では墓標を確認後に
アプリ管理下の共有コード、設定、状態、Firestore 永続キャッシュを削除する。ただし、二度と起動しない
端末、壊れた端末、古い Safari/PWA の別保存領域にはコピーが残り得る。

利用規約・画面では「90日後に削除」を無限定に言わず、`オンライン共有データを削除します。端末内や、
ご自身で保存したバックアップは自動では消えません` と範囲を示す。

### バックアップ

- 削除ジョブは JSON 書き出しなど利用者管理のコピーを探したり削除したりできない。
- 削除済みの共有世帯を Firebase 管理者が復旧する機能は用意しない。
- E2E 暗号化された内容をサーバー側で読んで個別復元することもできない。
- 期限前の警告に「必要なら設定から書き出す」を併記する。
- 削除後に手元の JSON から再開する場合は、**新しい共有コードで新しい世帯として**読み込む。同じコードは
  墓標により再利用できない。

クラウド側の災害復旧バックアップを別途有効にする場合、90日削除済みデータがバックアップに残る期間と
完全消去時期を保持方針へ明記する必要がある。現時点では「復元不能」を利用者向けの既定とする。

## 9. 段階導入

1. **仕様確定**: 下記の未決定事項、利用者向け文言、費用負担を決める。
2. **記録のみ**: 新フィールド、ルール、activity trigger を導入する。まだ削除しない。
3. **90日の観測期間**: 導入前からある文書は少なくとも導入日から90日間、削除対象にしない。
   `lastActivityAt` がない文書を即座に期限切れ扱いしない。
4. **警告表示**: 30日・7日・24時間の警告と「このまま使う」を公開する。
5. **dry-run**: scheduled function が削除候補の件数だけを記録し、文書は変更しない。
6. **限定有効化**: `retentionVersion` を付けた文書だけ墓標化・削除する。
7. **全面有効化**: エラー率、候補数、ルール拒否、費用を監視して対象を広げる。

公開順は必ず **ルールと墓標読み取り対応クライアント → 活動記録 → 警告 → 削除ジョブ** とする。
削除ジョブを先に有効にしない。

## 10. テスト計画

### 単体テスト

- 59日23時間59分、60日、82日23時間59分、83日、89日、90日の境界
- 夏時間や端末タイムゾーンに影響されず UTC で判定すること
- 数える操作／数えない操作の全一覧
- 「このまま使う」でサーバー時刻から90日に延びること
- 同じ scheduled job を複数回実行しても結果が変わらないこと

### Firestore Emulator / Rules テスト

- 墓標がある houseId の create/update が新旧クライアントとも拒否されること
- 墓標の list とクライアント write が拒否され、既知IDの get だけ許可されること
- クライアントが未来の `lastActivityAt` / `expiresAt` を偽造できないこと
- 既存の E2E 暗号化、フィールド allowlist、metrics のルールが退行しないこと
- 別世帯の墓標を列挙できないこと

### Functions Emulator / 統合テスト

- 期限切れだけが「墓標作成＋household削除」されること
- 削除直前の活動更新と競合した場合、活動済み文書が残ること
- 親端末の活動で子端末を含む世帯全体の期限が延びること
- オフライン端末の保留書き込みが削除後に拒否され、文書を復活させないこと
- 削除後に同じ共有コードで新規世帯を作れないこと
- 新しい共有コードとバックアップで新規開始できること
- `lastActivityAt` のない旧文書が観測期間中に削除されないこと

## 11. 運用監視

- dry-run 候補数、実削除数、競合保留数、失敗数
- activity trigger の失敗数と遅延
- 墓標による write 拒否の件数（IDや暗号文をログへ出さない）
- scheduled function の未実行、重複実行、処理時間、Firestore 読み書き費用
- 削除前後の問い合わせに答えるため、内容を含まない `deletedAt` と方針版だけ墓標に残す

「削除対象一覧」をクライアントから列挙する管理画面は作らない。必要なら IAM で保護した運用者用の
サーバー処理または Google Cloud Console から確認する。

## 12. 未決定事項

実装前に次を決める。

1. 90日を固定期間とするか、学校の長期休暇用途に合わせて120日などへ変更するか。
2. 「このまま使う」だけの操作を活動と数える方針でよいか。
3. 予告を30日・7日・24時間の3段階にするか。画面内通知だけで十分か。
4. 墓標を無期限保持するか。有限にするなら、古い端末の復活を防ぐ別の世代ID設計をどうするか。
5. 削除後、オンラインになった端末の localStorage を自動消去するか、確認後に消すか。
6. JSON バックアップから新しい共有コードへ復元する正式導線をどこに置くか。
7. Cloud Functions / Scheduler の Blaze 課金、予算アラート、障害通知の管理者を誰にするか。
8. Firestore のマネージドバックアップを使うか。使う場合、削除済みデータのバックアップ保持期間を
   利用者向け説明へどう記載するか。
9. `lastActivityAt` がない旧文書に対する観測期間の開始日をいつにするか。
10. 運用者向けの削除件数を既存の匿名登録数画面に出すか、Cloud Monitoring だけにするか。
